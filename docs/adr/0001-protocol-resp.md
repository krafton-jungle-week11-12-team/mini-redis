# ADR 0001: 통신 프로토콜로 RESP 사용

이 문서를 읽으면 mini-redis 서버와 클라이언트가 어떤 형식으로 바이트를 주고받는지, 왜 HTTP 대신 RESP를 골랐는지 알 수 있어요.

- 상태: 채택
- 날짜: 2026-11-13

## 결정

mini-redis 서버는 RESP(Redis Serialization Protocol)로 요청을 받고 응답해요.

## 비교

| 항목 | HTTP | RESP |
| --- | --- | --- |
| 한 줄 요약 | 누구나 쉽게 부를 수 있지만 무겁다 | Redis 전용이라 가볍고 빠르다 |
| 바이트 파싱 | 요청 줄, 헤더, Content-Length, body를 차례로 읽어야 해서 복잡하다 | `*`(인자 개수)와 `$`(길이)만 읽으면 돼서 간편하다 |
| 명령어 매핑 | 필요하다. HTTP 메서드(GET, PUT, DELETE 등)와 경로를 Redis 명령어(GET, SET, DEL 등)에 대응시켜야 한다 | 필요 없다. 명령어 이름을 첫 인자로 그대로 보낸다 |
| 브라우저 접근 | 브라우저에서 바로 mini-redis를 부를 수 있다 | 브라우저가 직접 부를 수 없어서 중간에 웹 백엔드 서버가 필요하다 |
| 이후 단계 확장 (Phase 4~6) | 만료·무효화·영속성마다 매핑과 형식을 새로 설계해야 한다 | 명령어 테이블 추가, 서버 push, AOF 파서 재사용으로 확장하기 쉽다 |

## 요청과 응답 흐름

사용자가 입력한 명령어는 클라이언트가 RESP로 바꿔서 서버에 보내고, 서버의 RESP 응답은 클라이언트가 다시 읽기 쉬운 값으로 바꿔요.

```
사용자 ──"SET name kim"──→ 클라이언트 ──*3\r\n$3\r\nSET...──→ 서버
사용자 ←──── "OK" ──────── 클라이언트 ←──── +OK\r\n ──────── 서버
```

## 결과

- 파싱은 `*`와 `$`만 읽으면 돼서 서버 구현이 간단해져요.
- 명령어 이름을 그대로 보내므로 HTTP 메서드·경로 매핑을 설계하지 않아도 돼요.
- Phase 4~6(만료, 무효화, 영속성)에서 명령어 테이블 추가, 서버 push, AOF 파서 재사용으로 확장해요.
- 브라우저는 mini-redis를 직접 부를 수 없어요. 브라우저에서 쓰려면 중간에 웹 백엔드 서버를 둬야 해요.
