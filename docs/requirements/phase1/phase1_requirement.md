# Mini Redis Phase 1 요구사항 명세서

Phase 1(해시 테이블 & 서버)에서 구현할 요구사항이에요. 요구사항 ID는 분류 순서를 바꾸기 전의 번호를 그대로 써요.

## 1. 서버

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-16 | 사용자는 명령어로 서버를 켜고 끌 수 있어야 한다. | |
| R-17 | 사용자는 서버가 살아있는지 확인할 수 있어야 한다. | |
| R-18 | 서버는 모든 명령어 요청에 대해 동일한 구조의 응답을 반환해야 한다. | |
| R-19 | 사용자가 유효하지 않은 형태의 명령어를 입력하면, 서버는 오류를 반환해야 한다. | |

## 2. 해시테이블

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-01 | 레디스는 key-value 데이터를 저장하기 위한 해시테이블을 가지고 있어야 한다. | |
| R-02 | 레디스는 해시테이블의 초기 배열 크기를 100칸으로 생성해야 한다. | |
| R-03 | 레디스는 해시테이블이 꽉 차면 해시테이블을 확장해야 한다. | |
| R-04 | 레디스는 요청받은 key가 이미 값이 차 있는 index로 변환되면(collision), 비어 있는 가장 가까운 index를 찾아 저장해야 한다. | |

## 3. 해시 함수

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-05 | 레디스는 요청받은 key를 해시 함수를 사용해 해시테이블의 index로 변환해야 한다. | |
| R-06 | 해시 함수는 어떤 자료형이든 입력받아 해시테이블 크기 내의 정수(0 ~ SIZE-1)를 반환해야 한다. | |

## 4. 데이터 규칙

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-07 | 사용자는 key에 해당하는 value값으로 NULL을 입력할 수 없다. | 조회 결과가 null(없음)인 경우는 해당 key가 저장된 적이 없거나 삭제된 경우 또는 해당 key의 TTL이 만료된 경우 |
| R-08 | 레디스는 value에서 NULL과 빈 문자열("")을 구분해야 한다. | |

## 5. 명령어

### 5.1 SET

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-09 | 사용자는 SET key value를 입력해 저장소에 데이터를 저장할 수 있어야 한다. 레디스는 key가 변환된 index 위치에 value를 삽입해야 한다. | |
| R-10 | 사용자가 이미 존재하는 key에 대해 SET을 요청하면, 레디스는 기존 값을 덮어써야 한다. | |

### 5.2 GET

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-11 | 사용자는 GET key를 입력해 key에 해당하는 value를 조회할 수 있어야 한다. | |
| R-12 | 레디스는 key에 해당하는 value가 없으면 nil을 반환해야 한다. | |

### 5.3 DEL

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-13 | 사용자는 DEL key를 입력해 데이터를 삭제할 수 있어야 한다. 레디스는 key 위치의 value를 비우고(NULL), 삭제한 개수를 응답해야 한다. | |

### 5.4 EXISTS

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-14 | 사용자는 EXISTS key를 입력해 key 존재 여부를 확인할 수 있어야 한다. 레디스는 key가 저장소에 있으면 1을, 없으면 0을 응답해야 한다. | 예: `EXISTS user:1:name` |

### 5.5 DBSIZE

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-15 | 사용자는 저장소에 저장된 데이터 개수를 확인할 수 있어야 한다. | |
