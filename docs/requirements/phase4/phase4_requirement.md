# Mini Redis Phase 4 요구사항 명세서

이 문서를 읽으면 Phase 4(만료)에서 key에 만료 시간을 붙이고, 만료된 key를 지연 만료와 만료 청소기로 정리하는 규칙을 확인할 수 있어요. 요구사항 ID(R-51 ~ R-80)는 설계·테스트·구현에서 이 문서를 참조하는 기준이에요.

1차 범위는 1 ~ 7장(R-51 ~ R-70)이에요. 8장 만료 청소기(R-71 ~ R-80)는 **2차 범위**라서 1차에서는 구현하지 않아요.

## 1. 만료

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-51 | 사용자는 key에 만료 시간(초)을 지정할 수 있어야 한다. | 예: `SET key1 val1 300` |
| R-52 | 레디스는 만료 시간이 1 ~ 1,728,000 사이의 정수가 아니면 오류를 반환해야 한다. | 최댓값 1,728,000초는 20일이에요 |
| R-53 | 레디스는 요청을 받은 시각에 지정한 초를 더해 만료 시각으로 저장해야 한다. | |
| R-54 | 레디스는 만료 시각을 YYYY-MM-DD HH:MM:SS 형식으로 저장해야 한다. | 지연 만료(R-58) 때 이 시각과 현재 시각을 비교해요. 시간대 기준(UTC / 로컬)은 설계에서 정해요 |
| R-55 | 사용자가 이미 만료 시간이 있는 key에 만료 시간을 다시 지정하면, 레디스는 새 시간으로 바꿔야 한다. | |

## 2. 버킷 필드

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-56 | 해시테이블의 각 버킷은 만료 시각을 저장하는 필드를 가져야 한다. | R-20의 버킷 필드에 추가해요 |
| R-57 | 레디스는 만료 시간이 없는 key의 만료 시각 필드를 '만료 없음' 값으로 저장해야 한다. | `None` 유력. `-1` 등 다른 값과 비교해 설계에서 확정해요 |

## 3. 지연 만료

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-58 | 레디스는 key를 조회하는 요청이 들어오면 그 key의 만료 여부를 확인해야 한다. | GET, EXISTS, TTL 등 key를 조회하는 모든 명령어에서 확인해요 |
| R-59 | 레디스는 현재 시각이 만료 시각과 같거나 지났으면 key를 만료된 것으로 판정해야 한다. | 예: TTL이 10초면 정확히 10초 뒤부터 만료예요 |
| R-60 | 레디스는 조회한 key가 만료됐으면 그 버킷의 state를 TOMBSTONE으로 바꿔야 한다. | EMPTY로 바꾸면 충돌로 밀려난 뒤쪽 key의 탐사가 끊겨서 TOMBSTONE으로 바꿔요 |
| R-61 | 레디스는 만료된 key를 모든 명령어에서 없는 key로 취급해야 한다. | 예: GET은 nil, EXISTS는 `0`, SETNX는 저장 성공 |

## 4. 덮어쓰기

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-62 | 사용자가 만료 시간 없이 SET으로 기존 key를 덮어쓰면, 레디스는 그 key의 만료 시간을 없애야 한다. | 예: `SET key1 val1 30` → `SET key1 val1`이면 만료 없음 |
| R-63 | 사용자가 GETSET, SETXX, MSET으로 기존 key를 덮어쓰면, 레디스는 그 key의 만료 시간을 없애야 한다. | 실제 Redis와 같아요 |
| R-64 | 사용자가 INCR·DECR로 값을 바꾸면, 레디스는 그 key의 만료 시간을 유지해야 한다. | 예: `SET views 10 60` → `INCR views`이면 60초 유지. 실제 Redis와 같아요 |

## 5. TTL

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-65 | 사용자는 TTL key로 key의 남은 만료 시간(초)을 확인할 수 있어야 한다. | 예: `TTL key1`. 만료된 key의 응답(nil 등)은 설계에서 정해요 |

## 6. 리해싱

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-66 | 레디스는 적재율이 0.75를 넘으면 해시테이블을 확장하기 전에 만료 시각이 지난 key를 삭제해야 한다. | 만료 key를 찾으려면 전체 버킷을 순회해야 하지만, 이어지는 확장도 전체 순회라 함께 처리해요 |
| R-67 | 레디스는 만료된 key를 삭제한 뒤 적재율이 0.5 이하면, 해시테이블 크기를 그대로 두고 다시 정리해야 한다. | TOMBSTONE도 같이 지워요. SET·DEL이나 만료가 반복돼도 테이블이 끝없이 커지지 않게 해요 |
| R-68 | 레디스는 만료된 key를 삭제한 뒤에도 적재율이 0.5를 넘으면 해시테이블을 확장해야 한다. | |
| R-69 | 레디스는 해시테이블을 확장하거나 다시 정리할 때 남은 key의 만료 시각을 그대로 유지해야 한다. | |

## 7. DBSIZE

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-70 | 레디스는 DBSIZE 결과에 아직 정리되지 않은 만료 key를 포함할 수 있다. | R-19의 예외예요. 정확히 세려면 매번 전체 버킷을 순회해야 해요. 실제 Redis와 같아요 |

## 8. 만료 청소기 (2차)

> **2차 범위예요.** 1차에서는 지연 만료(R-58 ~ R-61)와 리해싱(R-66 ~ R-69)으로만 만료 key를 정리하고, 이 장의 요구사항은 구현하지 않아요.

| ID | 요구사항 | 비고 |
| --- | --- | --- |
| R-71 | 레디스는 아무도 조회하지 않는 만료 key가 남지 않도록, 만료된 key를 주기적으로 정리하는 만료 청소기를 가져야 한다. | 2차 |
| R-72 | 레디스는 만료 시간이 있는 key 목록을 따로 관리해야 한다. | 2차. 만료 청소기가 이 목록에서 key를 골라요 |
| R-73 | 만료 청소기는 1초에 최대 5번 실행되어야 한다. | 2차 |
| R-74 | 만료 청소기는 만료 시간이 있는 key 중 state가 OCCUPIED인 key만 골라야 한다. | 2차 |
| R-75 | 만료 청소기는 만료 시간이 있는 key의 1%(최대 200개)를 무작위로 골라야 한다. | 2차 |
| R-76 | 만료 청소기는 만료 시간이 있는 key가 20개 이하이면 전부 골라야 한다. | 2차 |
| R-77 | 만료 청소기는 고른 key 중 만료된 key의 state를 EMPTY나 TOMBSTONE으로 바꿔야 한다. | 2차. EMPTY로 바꾸면 탐사가 끊길 수 있어요(R-60). TOMBSTONE으로 통일할지 설계에서 정해요 |
| R-78 | 만료 청소기는 고른 key 중 만료된 key가 25% 이상이면 다시 골라야 한다. | 2차. 재선택 반복은 100ms 제한(R-79) 안에서만 해요 |
| R-79 | 만료 청소기는 실행 시간이 100ms를 넘으면 강제 종료해야 한다. | 2차 |
| R-80 | 만료 청소기는 명령어를 처리하는 스레드와 같은 스레드에서 실행되어야 한다. | 2차. R-41의 단일 스레드 원자성 전제를 깨지 않게 해요 |
